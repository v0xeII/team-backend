# Командное задание backend: «Заявки на пропуск»

**Максимум — 35 баллов.** Реализуйте REST API, через которое сотрудники подают заявки на посещение организации гостем, просматривают их и отменяют до рассмотрения. Охрана принимает решение через служебный API. Клиент и сервер проверяются независимо.

## Сценарий и данные

Сотрудник входит в систему по выданному четырёхсимвольному коду. Он видит только свои заявки, может создать заявку и отменить её, пока статус равен `PENDING`. Охрана может одобрить или отклонить заявку. Одобренная заявка сама по себе не создаёт пропуск.

В базе используются таблицы `staff` и `pass_request`; схему и начальные данные создают миграции Liquibase. Сотрудник имеет автоматически генерируемый `id`, уникальный `code` и `full_name`. Заявка содержит автоматически генерируемый `id` (`Long`), ссылку на автора (`host_id`), `full_name`, `phone`, необязательные `organization` и `comment`, `purpose`, `valid_from`, `valid_to`, `status`, `created_at` и `updated_at`. Не связывайте реализацию с учебными кодами и ID: при проверке используются другие данные.

Статусы и единственные допустимые переходы:

| Текущий статус | Действие                 | Кто выполняет | Новый статус |
| -------------- | ------------------------ | ------------- | ------------ |
| `PENDING`      | Одобрить                 | Охрана        | `APPROVED`   |
| `PENDING`      | Отклонить с комментарием | Охрана        | `REJECTED`   |
| `PENDING`      | Отменить                 | Автор заявки  | `CANCELLED`  |

Все остальные переходы, в том числе повтор того же действия, завершаются ошибкой `409`.

## API и форматы

Обмен данными — JSON в UTF-8. Даты и время имеют формат `yyyy-MM-dd'T'HH:mm:ss` без смещения и трактуются в зоне `Europe/Moscow`. Серверные отметки `createdAt` и `updatedAt` сохраняются и возвращаются с точностью до секунды. Доли секунды отбрасываются без округления. Текущее время берите только из внедрённого `Clock`.

| Метод и путь                            | Назначение                            | Успешный ответ                     |
| --------------------------------------- | ------------------------------------- | ---------------------------------- |
| `GET /api/{code}/auth`                  | Получить профиль сотрудника           | `200`, `{"name":"ФИО сотрудника"}` |
| `GET /api/{code}/requests`              | Получить заявки сотрудника            | `200`, массив                      |
| `GET /api/{code}/requests?status=...`   | Получить заявки с фильтром по статусу | `200`, массив                      |
| `GET /api/{code}/requests/{id}`         | Получить детали своей заявки          | `200`, объект деталей              |
| `POST /api/{code}/requests`             | Создать заявку                        | `201`, объект деталей              |
| `POST /api/{code}/requests/{id}/cancel` | Отменить свою заявку                  | `200`, объект деталей              |
| `PATCH /api/admin/requests/{id}`        | Изменить статус заявки                | `200`, объект деталей              |

Элемент списка содержит `id`, `fullName`, `validFrom`, `validTo`, `status`. Объект деталей содержит `id`, `fullName`, `phone`, `organization`, `purpose`, `validFrom`, `validTo`, `status`, `comment`, `createdAt`, `updatedAt`. Поля `organization` и `comment` всегда присутствуют; если значения нет, передавайте `null`.

Код сотрудника — ровно четыре ASCII-символа из `A–Z`, `a–z` и `0–9`. Регистр значим, пробелы не удаляются. Неверный формат возвращает `400 {"error":"Invalid code format"}`, неизвестный код — `401 {"error":"Unauthorized"}` на всех пользовательских маршрутах.

Список включает только заявки текущего сотрудника и сортируется по возрастанию `validFrom`, затем по возрастанию `id`. Если заявок нет, верните `[]`. Фильтр принимает только `PENDING`, `APPROVED`, `REJECTED` или `CANCELLED`. Пустое, неизвестное значение, пробелы или другой регистр возвращают `400 {"error":"Invalid status"}`.

Чужая или отсутствующая заявка при чтении или отмене возвращает `404 {"error":"Request not found"}`. Для служебного маршрута требуется правильный заголовок `X-Admin-Key`; иначе ответ — `403 {"error":"Forbidden"}`. Если заявка для охраны отсутствует, верните тот же `404`.

## Создание заявки

Тело `POST /api/{code}/requests` содержит строковые поля `fullName`, `phone`, `organization`, `purpose`, `validFrom`, `validTo`. Автор определяется по коду сотрудника. Новая заявка получает статус `PENDING`, `comment: null`, а `createdAt` и `updatedAt` равны текущему времени из `Clock` после усечения до секунды.

Перед проверкой и сохранением удалите пробелы в начале и конце каждой строки.

- `fullName`: обязательно, от 5 до 150 символов.
- `phone`: обязательно, формат `+7` и ровно десять ASCII-цифр; пробелы и разделители внутри запрещены.
- `organization`: необязательно, не более 150 символов. Пропущенное, `null` или пустое после обрезки значение сохраняйте как `null`.
- `purpose`: обязательно, от 5 до 200 символов.
- `validFrom` должен содержать корректную дату указанного формата. Начало должно быть не раньше точного текущего времени из `Clock` с учётом долей секунды. Если часы показывают `10:00:00.500`, начало в `10:00:00` недопустимо, а в `10:00:01` допустимо. Если часы показывают ровно `10:00:00`, начало в `10:00:00` допустимо.
- `validTo`: обязательная корректная дата точного формата; значение должно быть позже `validFrom` и приходиться на тот же календарный день.

На все доступные ошибки валидации ответьте сразу: `400 {"errors":{"field":"непустое сообщение",...}}`. Имена полей фиксированы, тексты сообщений свободные. Для сравнения дат используйте только успешно разобранные значения.

## Дубликаты и смена статуса

Заявка считается дубликатом, если у того же автора есть заявка с тем же нормализованным телефоном в статусе `PENDING` или `APPROVED` и интервалы пересекаются: `newFrom < existingTo && existingFrom < newTo`. Совпадение границ без пересечения разрешено. Заявки других авторов, с другими телефонами или в статусах `REJECTED` и `CANCELLED` не мешают созданию. Дубликат возвращает `409 {"error":"Duplicate request"}`.

Автор может отменить только заявку со статусом `PENDING`; результат — `CANCELLED`.

Тело запроса охраны имеет вид `{"status":"APPROVED"}` либо `{"status":"REJECTED","comment":"Причина"}`. Удалите крайние пробелы у статуса и комментария. Для `REJECTED` комментарий обязателен и должен содержать от 1 до 500 символов. Для `APPROVED` строковый комментарий игнорируйте и сохраняйте `null`. Недопустимый целевой статус возвращает ошибку поля `status`, некорректный комментарий — ошибку поля `comment`. Любой запрещённый переход возвращает `409 {"error":"Invalid status transition"}`.

При создании заявки и решении охраны заготовка разбирает тело запроса до проверки значений полей. Если тело не удаётся разобрать из-за некорректного JSON или недопустимого типа поля, заготовка возвращает `400 {"error":"Invalid request body"}`.

- Список заявок — проверка кода → проверка параметра `status`.
- Чтение деталей и отмена сотрудником — проверка кода → наличие и принадлежность заявки → допустимость перехода при отмене. Тело для отмены не требуется.
- Решение охраны — проверка `X-Admin-Key` → разбор тела → наличие заявки → валидация полей → допустимость перехода.
- Создание — разбор тела → проверка кода → валидация полей → поиск дубликата.

Запись заявки и смена статуса должны сохраняться в PostgreSQL транзакционно. При ошибке база данных не меняется. При успехе `createdAt` сохраняется, а `updatedAt` берётся из `Clock`; если часы не изменились, эти значения могут совпасть. Не кешируйте данные: проверки могут изменять БД напрямую.

## Ограничения заготовки

Реализуйте доменную модель, репозитории и API в предоставленных для участника файлах. Схему базы данных создаёт Liquibase; Hibernate должен проверять её (`ddl-auto: validate`), а не создавать или обновлять. При проверке из заготовки восстанавливаются следующие защищённые файлы и каталоги; изменения в них не учитываются:

- `build.gradle.kts`, `settings.gradle.kts`, `gradle.properties`;
- весь каталог `src/main/resources/`, включая настройки приложения и миграции Liquibase;
- `src/test/resources/`, включая тестовый профиль;
- `src/main/kotlin/ru/nto/team/Application.kt`;
- `src/main/kotlin/ru/nto/team/ClockConfiguration.kt`;
- `src/main/kotlin/ru/nto/team/RequestBodies.kt`;
- `src/main/kotlin/ru/nto/team/JsonConfiguration.kt`;
- `src/main/kotlin/ru/nto/team/MalformedBodyAdvice.kt`;
- `src/main/kotlin/ru/nto/team/AdminKeyInterceptor.kt`;
- `src/main/kotlin/ru/nto/team/WebConfiguration.kt`;
- проверяющий код организаторов.

В остальных файлах `src/main/kotlin/ru/nto/team/` реализуйте требования задания; дополнительные классы и собственные тесты добавлять можно. Каждое сохраняемое свойство сущности заявки должно соответствовать ровно одной колонке `pass_request`; вычисляемые свойства (`@Formula`, коллекции) в сущности не используйте, для производных значений применяйте `@Transient` или DTO. Проверка выполняется по HTTP, JPA-метаданным и PostgreSQL, а не по именам классов или сервисов.
